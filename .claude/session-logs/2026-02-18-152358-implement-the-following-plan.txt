│ Plan: LMMS Project Format Migration — XML to SQLite                          │
│                                                                              │
│ Context                                                                      │
│                                                                              │
│ LMMS stores all project data as a monolithic XML document (.mmp/.mmpz). This │
│  architecture has severe problems:                                           │
│ - No indexing — PatternTracks are identified by position in an array, not by │
│  ID                                                                          │
│ - Fragile state — simple operations like reordering tracks can corrupt data  │
│ - No atomic writes — partial saves can corrupt project files                 │
│ - Opaque structure — the entire project must be parsed to access any part of │
│  it                                                                          │
│ - Song-level InstrumentTracks coexist with PatternTracks in the Song,        │
│ creating confusion                                                           │
│                                                                              │
│ This plan covers two parallel efforts:                                       │
│ 1. A standalone conversion tool that reads .mmp XML and writes to a new      │
│ SQLite-based format (.lmms-db or similar)                                    │
│ 2. Design groundwork for eventually replacing LMMS's internal data layer     │
│                                                                              │
│ Design Decisions                                                             │
│                                                                              │
│ - SQLite over time-series DB — Analysis shows LMMS data is primarily         │
│ hierarchical configuration (tracks, instruments, effects, plugins). Only     │
│ Notes and AutomationNodes are time-indexed, and their cardinality per-clip   │
│ is too low (typically 8–256 notes) to benefit from time-series indexing.     │
│ SQLite provides ACID transactions, relational indexing, single-file          │
│ portability, and zero-server deployment.                                     │
│ - No Song-level InstrumentTracks — Our format will not support               │
│ InstrumentTracks directly in the Song. All instruments live in the           │
│ PatternStore. Song-level InstrumentTracks from imported .mmp files will be   │
│ converted to PatternTracks during migration.                                 │
│ - Plugin parameters as JSON blobs — 57+ plugins each have unique parameter   │
│ schemas. Rather than one table per plugin, we store plugin params as a JSON  │
│ column. SQLite's JSON1 extension allows querying into these if needed.       │
│ - Proper ID-based references — Every entity gets a UUID or auto-increment    │
│ ID. No more position-based identification.                                   │
