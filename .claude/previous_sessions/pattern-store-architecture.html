LMMS PatternStore Architecture

How Song, PatternTrack, PatternStore, InstrumentTrack, and MidiClip connect

1. The Two TrackContainers

LMMS has two separate TrackContainer instances that hold tracks:
• Song — the main song editor (accessed via Engine::getSong())
• PatternStore — the pattern editor grid (accessed via Engine::patternStore())

They are independent containers. The Song holds PatternTrack objects that reference columns in the PatternStore by index.

Each PatternTrack has a static s_infoMap mapping PatternTrack* → int patternIndex.
The patternIndex() method returns this integer. When a PatternClip plays, it tells the PatternStore to play column patternIndex.

3. PatternStore Grid (TrackContainer: PatternStore)

The PatternStore is a grid. Each row is an InstrumentTrack. Each column corresponds to a PatternTrack index. Each cell is a MidiClip (one per InstrumentTrack per column).

Key detail: Each InstrumentTrack in the PatternStore has N MidiClip objects in its m_clips vector — one per PatternTrack column. MidiClip[i] is stored at position TimePos(i, 0) which equals i * 192 ticks (at default 192 ticks/bar). So column index maps directly to clip vector index: track->getClip(patternIndex) returns the MidiClip for that column.

4. How PatternTrack References PatternStore

PatternTrack "Pattern 2" in Song
↓ PatternTrack::s_infoMap[this] → patternIndex = 2
↓ PatternTrack::play() calls Engine::patternStore()->play(..., 2)
↓ PatternStore iterates its InstrumentTrack rows
↓ Each InstrumentTrack plays getClip(2) → its MidiClip at column 2

5. Export: What Goes Into a .xppt File

6. XML Serialization Structure

6a. How a full project saves the PatternStore

The PatternStore is serialized inside the first PatternTrack's <patterntrack> settings node (see PatternTrack::saveTrackSpecificSettings which calls Engine::patternStore()->saveState() only when s_infoMap[this] == 0).
<!-- Inside Song's <trackcontainer> --> <track type="1" name="Pattern 0"> <!-- PatternTrack (Type::Pattern = 1) --> <patterntrack> <!-- PatternTrack settings node --> <trackcontainer type="patternstore"> <!-- ★ PatternStore lives HERE --> <track type="0" name="Bass"> <!-- InstrumentTrack (Type::Instrument = 0) --> <instrumenttrack vol="100" mixch="3" .../> <!-- instrument settings, effects, etc. --> <midiclip pos="0"> ... </midiclip> <!-- Column 0 MidiClip --> <midiclip pos="192"> ... </midiclip> <!-- Column 1 MidiClip --> <midiclip pos="384"> ... </midiclip> <!-- Column 2 MidiClip --> <midiclip pos="576"> ... </midiclip> <!-- Column 3 MidiClip --> <midiclip pos="768"> ... </midiclip> <!-- Column 4 MidiClip --> </track> <track type="0" name="Kick"> <!-- Another InstrumentTrack --> <instrumenttrack ... /> <midiclip pos="0"> ... </midiclip> <midiclip pos="192"> ... </midiclip> <midiclip pos="384"> ... </midiclip> ... </track> <!-- ... more InstrumentTracks ... --> </trackcontainer> </patterntrack> <patternclip pos="0" ... /> <!-- PatternClip on song timeline --> <patternclip pos="384" ... /> <patternclip pos="576" ... /> </track> <track type="1" name="Pattern 1"> <!-- 2nd PatternTrack --> <patterntrack/> <!-- empty — PatternStore only saved in 1st --> <patternclip pos="0" ... /> <patternclip pos="192" ... /> </track> <track type="1" name="Pattern 2"> <!-- 3rd PatternTrack --> <patterntrack/> <patternclip pos="384" ... /> </track>

6b. What a .xppt export file looks like

<!-- Pattern_2.xppt — exporting patternIndex=2 --> <patterndata> <track type="0" name="Bass"> <instrumenttrack vol="100" mixch="3" ... /> <!-- full instrument settings --> <midiclip pos="384"> <!-- ★ only column 2's MidiClip --> <note pos="0" key="48" len="96" ... /> <note pos="96" key="55" len="96" ... /> </midiclip> </track> <track type="0" name="Kick"> <instrumenttrack ... /> <midiclip pos="384"> <note ... /> </midiclip> </track> <track type="0" name="Pad"> <instrumenttrack ... /> <midiclip pos="384"> <!-- empty MidiClip (no notes) --> </midiclip> </track> <track type="0" name="Lead"> <instrumenttrack ... /> <midiclip pos="384"> <note ... /> </midiclip> </track> </patterndata>

8. Combined Workflow

Step 1: Export PatternTracks 0, 1, 2 → Pattern_0.xppt, Pattern_1.xppt, Pattern_2.xppt
Each .xppt has ALL InstrumentTrack rows + their single-column MidiClip
Step 2: Save Without PatternTracks → project_skeleton.mmpz
Skeleton has InstrumentTrack definitions (instruments, effects, mixer channels) but no MidiClip data
Step 3: Open skeleton, Import Pattern_0.xppt
Matches existing InstrumentTracks by row order → restores MidiClip data at column 0
Current bug: creates duplicate InstrumentTracks instead of matching existing ones
Step 4: Import Pattern_1.xppt, Pattern_2.xppt
Same matching — adds MidiClip data at columns 1, 2
Known bugs in current implementation:
1. Export skips MidiClips: The saveTrackSpecificSettings path may not serialize MidiClip data correctly — need to verify clip is actually being saved with note content.
2. Import duplicates InstrumentTracks: Always creates new InstrumentTracks instead of matching existing ones in the PatternStore.
3. Import JO-ID collisions: JournallingObject IDs from the exported file collide with existing IDs, causing crashes with large imports.
